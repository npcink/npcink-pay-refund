# 1.3.1 开发复盘与维护思路

本文记录 2026-07-08 这轮面向正式使用前的整理、配置说明、退款状态优化、安全性能检查、真实站点缓存问题修复，以及后续维护原则。

## 背景

本轮开发从“正式使用前是否还需要整理”开始，逐步扩展到：

- 项目目录和发布包清理
- 支付宝、微信配置字段说明
- 微信证书和私钥字段顺序调整
- 退款时间窗口设置
- 微信退款 `PROCESSING` 状态的自动同步
- 退款查询结果 UI 现代化
- 安全、性能、卸载、日志和导出行为检查
- 真实站点中 CSS/JS 资源缓存导致的新旧代码混用问题

核心目标不是新增复杂功能，而是把插件从“本地能跑”推进到“可正式安装、可解释、可回滚、可排查”的状态。

## 主要产品决策

### 配置页说明要靠近实际来源

支付宝和微信字段都补充了简短说明，原则是：

- 告诉用户字段从哪个官方后台位置获取
- 说明密钥字段留空会保留现有值
- 避免在保存配置阶段过度阻塞，但在执行真实 API 前必须检测必要字段

微信配置中特别区分：

- 商户号
- 商户 API 证书序列号
- 商户私钥 `apiclient_key.pem`
- 微信支付公钥 ID / 平台证书序列号
- 微信支付公钥 / 平台证书 PEM

证书序列号和商户私钥被放在相邻位置，因为它们来自同一组商户 API 证书材料，用户理解成本最低。

### 退款时间窗口可配置

早期逻辑固定 7 天，后来改成设置项：

- 默认 7 天
- 允许管理员设置 1 到 365 天
- 查询页说明、支付宝、微信后端校验统一使用该配置

这里的原则是：插件只做本地操作窗口控制，实际能否退款仍以支付通道和商户签约规则为准。

## 微信退款状态设计

真实微信退款可能先返回 `PROCESSING`，几秒后才变成 `SUCCESS`。因此不能把首次 `PROCESSING` 展示成失败，也不能立即写入成功记录。

当前设计：

- 发起退款后如果返回 `PROCESSING`，保存一条本地 pending option
- 前端进入 10 秒轮询，每 1 秒查询一次微信退款状态
- 查询到 `SUCCESS` 后，使用 pending 中保存的操作人、金额和原因写入退款记录
- 查询到 `CLOSED` 或 `ABNORMAL` 后，清理 pending 和锁
- 超过 10 秒仍未成功时，界面保持处理中，允许后续手动查询

关键原则：

- `PROCESSING` 是受理中，不是失败
- 本地退款记录只在微信明确成功后写入
- 自动查询是体验优化，不是唯一真相来源
- 手动查询必须能继续同步 pending 状态

## 幂等与重复退款保护

重复退款风险来自三类场景：

- 用户重复点击
- 网络超时后再次提交
- 微信长时间 `PROCESSING` 后本地锁过期

当前保护组合：

- 退款记录表有 `(n_order, n_type)` 唯一键
- 退款提交前使用本地 lock option
- 微信 `PROCESSING` 时保存 pending
- 再次发起同一微信订单退款前，先检查 pending 并查询状态，不直接再次 POST 退款
- 微信成功落库需要 pending 或明确 fallback 上下文，避免状态查询接口写入空操作人/空原因记录

这里的设计思路是：不要只依赖微信的 `out_refund_no` 幂等，插件本地也要能解释并阻止重复操作。

## 查询结果 UI

微信退款查询结果从旧表格升级为状态卡片：

- 成功、处理中、关闭、异常、未知分别有不同视觉状态
- 展示商户订单号、商户退款单号、退款金额、退款时间和通道状态
- 空值统一显示“暂无”

这个 UI 是后台工具界面，不做营销化设计；目标是让操作者快速判断退款处于哪个状态，以及下一步是等待、重查还是去支付商户平台处理。

## 安全与性能检查结论

本轮安全和性能检查后处理了以下问题：

- 微信状态查询接口不再无上下文写入成功记录
- 微信 pending 状态不再因 10 分钟锁过期而允许直接重复发起退款
- 微信和支付宝错误日志不再写完整支付网关响应体，只保留状态码、错误码、错误摘要和 request id 等排查信息
- 卸载时补充清理 `npcink_pay_refund_pending_wx_` 和 `npcink_pay_refund_lock_` 前缀 option
- 退款记录导出按钮去掉“全部”字样，并说明默认导出最新 5000 条

性能方面，当前没有引入新的高频前台逻辑。管理页资源只在对应后台页面加载；导出接口保留 5000 条上限，避免一次性拉取过多记录。

## 真实站点样式和自动查询失效的根因

真实站点出现“PHP 新模板生效，但 CSS 样式和 10 秒自动查询没有生效”的原因是资源缓存。

现象判断：

- 页面已经输出新版退款卡片内容，说明 PHP 文件已更新
- 样式缺失、自动轮询不运行，说明 CSS/JS 仍是旧文件
- 当时资源版本固定为 `?ver=1.3.0`，真实站点更容易被浏览器、CDN、缓存插件或安全插件缓存住

修复：

- 插件版本升到 `1.3.1`
- 后台 CSS/JS 版本改为 `插件版本 + 文件修改时间`
- 重新打包为 `build/npcink-pay-refund-1.3.1.zip`

后续维护原则：只要改动后台 CSS/JS，要么升插件版本，要么确保资源 URL 的版本参数会变化。

## 发布与验证方式

本轮不建议使用源码压缩包直接安装，必须使用 Composer 构建的 release zip，因为微信 SDK 依赖在 `vendor/` 中。

常用命令：

```bash
composer build:zip
```

安全验证可使用不覆盖本地插件目录的检查组合：

```bash
find . -path './vendor' -prune -o -path './build' -prune -o -name '*.php' -print0 | xargs -0 -n1 php -l
find admin/js -name '*.js' -print0 | xargs -0 -n1 node --check
composer validate --strict
composer audit
wp plugin check npcink-pay-refund --slug=npcink-pay-refund --format=json --exclude-directories=build,bin --exclude-files=.gitignore,.distignore --path="/Users/muze/Local Sites/test/app/public" --url="http://test.local" --allow-root --skip-plugins="magick-ai"
wp eval-file bin/smoke-admin.php --path="/Users/muze/Local Sites/test/app/public" --url="http://test.local" --allow-root --skip-plugins="magick-ai"
```

注意：如果本地 WordPress 插件目录使用 symlink 指向仓库，不要随意运行会强制安装插件包的命令，以免覆盖 symlink。

## 后续维护建议

- 真实站点首次安装后，优先检查浏览器网络面板中 CSS/JS URL 是否带 `1.3.1-文件时间戳`
- 真实退款联调时，保留微信商户平台状态截图和 WordPress 本地记录截图
- 如果后续要支持部分退款，需要重新设计 `out_refund_no` 生成规则、记录表唯一键和本地幂等模型
- 如果退款记录超过 5000 条成为常态，再做分页导出或 CSV 流式导出
- 如果接入订单系统状态回写，必须把“支付通道退款状态”和“业务订单状态”分开建模，避免支付成功但业务状态回写失败时无法排查
