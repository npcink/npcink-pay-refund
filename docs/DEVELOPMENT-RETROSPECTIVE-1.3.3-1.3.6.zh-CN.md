# 1.3.3–1.3.6 对抗式审查与发布工程复盘

本文归纳 1.3.3 到 1.3.7 的退款安全整改、对抗式审查、WordPress.org 审核与发布收尾。目标不是重复 changelog，而是留下后续开发可以直接复用的判断框架、状态机约束和证据边界。

## 截至 2026-07-26 的事实

| 层级 | 当前事实 | 能证明什么 |
| --- | --- | --- |
| GitHub `main` / Release | `main` 与最新 Release 为 `v1.3.3` | 公开 GitHub 稳定线停在 1.3.3 |
| 开发分支 | 草稿 PR #2 包含 1.3.4 退款安全改造、1.3.5 包清理和 1.3.6 安全依赖更新 | 代码可审阅，不等于已合并 |
| WordPress.org | `1.3.5` 已发布，SVN 修订 `r3623533` | 目录安装包已进入公开发布渠道 |
| 自动化验证 | 本地与 CI 验证状态以当前提交为准 | 只覆盖代码、打包和受控烟测 |
| 真实商户验证 | 仍由商户操作者执行 | 未执行前不能声称支付宝或微信线上退款通过 |

这种状态并不整齐：WordPress.org 已经领先 GitHub `main` 和 GitHub Release。后续收口时应让 PR 通过 CI，再根据真实商户验证结果决定合并、打 tag 和创建 GitHub Release；不要用 WordPress.org 已发布来推导 GitHub 稳定线已经同步。

## 问题如何演进

### 1.3.3：先修基础安全和目录审核阻塞

这一阶段解决了发布前已经能明确证明的问题：

- WordPress.org `Contributors` 与真实账号对齐，移除平台已自动处理的手动翻译加载。
- Composer、插件头和 readme 的最低 PHP 统一到 8.1。
- 微信全额退款使用订单原总额，覆盖代金券导致实付额小于订单额的场景。
- 本地退款记录写入失败时保留重复退款锁和对账标记；本地补记不再调用支付提供方。
- 支付宝不再把无效占位回调地址放进签名请求。

这里形成了第一个核心原则：**支付提供方已经可能成功时，本地失败不能自动退化为再次发起退款。**

### 1.3.4：把“报错”拆成明确失败与结果不明

对抗式审查把关注点从正常成功路径移到网络断开、超时、签名失败、响应不完整和本地审计写入失败。审查结论先作为假设，再回到锁定版本的 SDK 源码、实际调用路径和可重复测试中裁决。

最终形成的状态机约束是：

1. 在调用提供方前生成稳定的退款请求号，并保存不含密钥和网关原文的最小请求上下文。
2. 返回成功必须经过官方 SDK 的验签路径，并核对订单号、退款请求号和金额。
3. 超时、网络错误、原文响应、字段不完整或标识不匹配都进入“结果不明”，不得当作明确失败。
4. 结果不明时保留重复退款锁，下一步先查询原退款请求。
5. 只有提供方明确证明原退款不存在时，才允许复用同一请求号和同一组参数重试。
6. 本地审计补记与提供方退款调用分离；修复本地记录时不得再次请求退款。

支付宝与微信的具体边界不同：

- 支付宝使用稳定 `out_request_no`，通过退款查询核对原请求；只有明确未查询到退款才允许原参数重试。
- 微信使用稳定且长度受限的 `out_refund_no`；只有新鲜、验签成功的 `404 RESOURCE_NOT_EXISTS` 才能证明可重试。其他 404、鉴权失败、超时、`SYSTEM_ERROR` 或未知响应都继续保留 pending 与锁。

### 1.3.5：把最终 ZIP 当作独立产品边界

WordPress.org 审核暴露了另一类问题：Plugin Check 通过并不代表安装包内容适合公开分发。候选 ZIP 仍包含维护文档和 EasySDK Tea 源规格文件，因此 1.3.5 调整 `.distignore`，保留运行所需 Composer 依赖，排除工程过程材料和非运行时源规格。

由此得到第二个核心原则：**审查源码树不能替代审查最终安装包。** 发布判断必须针对将要安装或上传的精确 ZIP，而不是工作区、构建脚本或一次绿色静态检查。

### 1.3.6：安全公告到达后保持版本不可变

1.3.5 发布后，`composer audit` 新增了 Guzzle 7.15.1 之前版本的 4 条中危公告。候选分支把 Guzzle 7.13.2 升级到 7.15.1，并同步升级 Promises 2.5.1 与 PSR-7 2.13.0。

公开的 1.3.5 包不能被修复后的不同依赖内容静默替换，因此更新后的精确制品必须使用 1.3.6。这里形成第三个核心原则：**版本号标识不可变制品；安全依赖变化也必须产生新版本和新验证证据。**

### 1.3.7：收紧退款操作边界

1.3.7 移除订单号静默改写，增加异常退款队列、操作者隔离和独立退款 capability；微信退款在 `CLOSED/ABNORMAL` 后推进新的商户退款单号。插件只负责后台退款操作和退款记录，不再拦截退款专员的其他 WordPress 后台页面。

## 对抗式审查的正确用法

`npcink-eval-lab` 适合寻找正常评审容易忽略的反例，但输出不是事实判决。可复用流程是：

1. 先写出不可破坏的不变量，例如“同一订单不能因结果不明而产生第二笔退款”。
2. 让审查者从超时、重放、签名、状态错配、本地写失败和并发方向攻击不变量。
3. 把发现分成已证实、待证实和不成立，不直接把模型意见写进代码。
4. 对每个高风险发现回查锁定依赖源码、真实接口契约和现有调用路径。
5. 用故障注入或确定性单元测试固定证据，再实施最小修正。
6. 重新审查失败路径，确认修复没有把风险转移到解锁、重试或本地补记路径。

本次最有价值的反例不是“接口返回失败”，而是“提供方已受理，但本地没收到可信结果”。这类歧义必须建模为一等状态，不能塞进通用异常分支。

## 发布证据必须分层

| 证据 | 能证明 | 不能证明 |
| --- | --- | --- |
| 单元测试 | 状态机与关键纯逻辑符合预期 | 真实 SDK 网络调用成功 |
| PHP 8.1 / 8.4 CI | 两档解释器下仓库验证可运行 | 真实 WordPress 站点或商户可用 |
| 本地 WordPress 烟测 | 安装包可安装、后台关键路径存在 | 支付提供方退款成功 |
| Plugin Check | 已覆盖规则没有报告问题 | WordPress.org 人工审核必过 |
| ZIP 清单审阅 | 精确安装包包含和排除了预期文件 | 远端渠道已经发布 |
| Git push / PR | 源码可追溯、可审阅 | 已合并、已发布或已上线 |
| SVN 远端修订 | WordPress.org 目录内容已提交 | GitHub Release 已同步 |
| 真实商户低风险退款 | 指定凭据、订单和包下的真实调用结果 | 所有商户和所有异常都正确 |

以后文档和发布说明应直接写证据名称，避免使用含混的“已验证”“已完成发布”。

## 这次暴露的工程反模式

- 在版本一致性测试中硬编码 `1.3.4`，版本升到 1.3.5 后 CI 才暴露遗漏。版本测试应从插件头读取当前版本，再核对运行时常量和 `Stable tag`。
- 把安全审计失败误报为网络抖动并直接重试，会掩盖真实公告；重试仍返回同一公告时应按依赖风险处理。
- 真实商户清单固定引用旧候选 ZIP，容易让操作者验证错误制品。清单应同时记录当前公开版本和“以后使用构建命令输出的精确版本化 ZIP”。
- 把 Plugin Check 绿色当作目录审核完成，遗漏最终包中的过程文档和依赖源规格。
- 看到提供方调用抛异常就释放锁或更换请求号重试，可能把网络歧义放大成重复退款。
- 把 GitHub、WordPress.org、真实支付验证合并成一个“发布完成”状态，导致状态不可审计。

## 后续版本的推荐顺序

1. 先执行 `git status --short --branch`，识别并保护现有工作。
2. 写出本次变更影响的支付不变量和明确的失败关闭规则。
3. 先补测试，至少覆盖成功、明确不存在、结果不明、验签失败、本地写失败和重复提交。
4. 同步插件头、运行时常量、`readme.txt` 和 changelog。
5. 执行 `composer verify`，生成唯一版本化 ZIP。
6. 回读 ZIP 内的版本、`vendor/autoload.php` 和完整文件清单；记录 SHA-256。
7. 对高风险差异做对抗式审查，并逐条以代码、契约或测试裁决。
8. 在受控订单上按 `REFUND-INTEGRATION-CHECKLIST.md` 完成真实商户验证。
9. 分别记录 Git 合并/tag/Release、WordPress.org SVN 修订和真实商户结果。

## 下一阶段

当前最小闭环是：

- 修复并保持 PR #2 的 PHP 8.1 / 8.4 CI 绿色；
- 由商户操作者使用精确 1.3.7 ZIP 完成支付宝、微信低风险退款与结果不明恢复验证；
- 验证通过后再决定是否将当前变更合入 `main`、补齐 `v1.3.7` tag 和 GitHub Release；
- 发布 WordPress.org 1.3.7 前，重新检查精确 ZIP、远端 SVN 修订和目录元数据；
- 后续版本继续复用稳定请求号、查询优先和精确制品证据，不重新发明退款状态机。

无论后续版本号如何变化，都不应降低“结果不明时不重复退款”和“真实商户证据由操作者确认”这两条门槛。
